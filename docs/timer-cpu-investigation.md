# Timer conflict CPU investigation

On 2026-11-04, the Whiteboard project dashboard showed CPU near saturation over the preceding 24 hours, dominated by user CPU with much smaller system CPU and near-zero I/O wait. A Supabase warning arrived at 11:50 Asia/Manila. The PostgreSQL log stream contained about 86,000 sampled `Timer changed in another client` errors in 24 hours; samples identified PostgREST 14.5, SQLSTATE 40001, and `transition_board_timer`. Concurrent calls were observed waiting on timer locks. A single database session's log sequence advanced far faster than the ingested log count, so the sampled count is not the total number of attempts.

Supabase documents that PostgREST 14 can retry a deterministic 40001 indefinitely, even for a stale application revision. The timer RPC deliberately raises 40001 for that condition. This closely matches the observed sustained errors and high user CPU, and is a strong causal diagnosis, but a post-fix production comparison is needed to verify the CPU impact. The existing PR's cursor and viewport changes reduce browser work; they do not correct this database retry loop.

The migration preserves SQLSTATE 40001 for direct SQL callers. When PostgREST supplies its transaction-local `request.method`, the function instead raises P0001 with the same message, preserving the existing application's generic error handling and refresh-on-conflict behavior while preventing PostgREST 14 from retrying that deterministic conflict. HTTP consumers that inspect a conflict's SQLSTATE should note the change: in the affected version the old HTTP request can remain trapped in the retry loop. Local isolated Postgres tests cover both contexts and concurrent writers. The migration was applied to the Whiteboard production Supabase project on 2026-11-04 as migration version `20261104053442` and verified with `pg_get_functiondef`. At the verification instant no `authenticator` sessions executing `transition_board_timer` were visible. Existing requests from before deployment may still require separate operational intervention if retrying processes reappear. A real post-session CPU comparison remains pending.

The project gateway recorded, over its available log window, hundreds of requests each to admin settings, presence, timer reads and board shards. These counts are not per-session attribution. Board socket subscriptions dispose after their final listener leaves; pending persistence uses bounded exponential retries and retains recoverable local data. Global settings and open admin-panel polling now skip hidden tabs and refresh on return. The cursor and viewport changes reduce browser work but do not by themselves resolve the database retry loop. Compare CPU components, timer error rates and connections during and after a real session after deployment to confirm the effect.

For the browser clipboard regression, start the app locally with `VITE_LOCAL_SANDBOX=true`, then run `npm run test:browser` with Chrome installed (or set `BROWSER_CHANNEL=chromium` after installing Playwright Chromium). It exercises trusted native clipboard events against local-only fixtures, including image asset metadata, linked selection, repeated paste, group undo/redo, permission-independent duplicate, and an external PNG.
